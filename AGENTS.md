# DBTuna engineering

The extension host in `src/extension` owns all VS Code and PostgreSQL access. The React webview consumes the canonical graph only. `packages/plan-core` owns Zod schemas and graph invariants; `adapter-sdk` defines the adapter boundary; `adapter-postgres` owns native mappings and parsing.

Use strict TypeScript. Preserve unknown native attributes, optional metrics and child order. Never interpret optimizer costs as milliseconds. React must render native strings as text.

Development: `npm install`, `npm run build`, `npm run typecheck`, `npm test`, `npm run lint`, `npm run test:vscode`. `npm run test:postgres:docker` provisions an isolated PostgreSQL container on localhost:55439 and removes it afterward. The lower-level `npm run test:postgres` requires explicit DBTUNA_POSTGRES_TEST=1 and DBTUNA_POSTGRES_TEST_PASSWORD for a disposable instance.

Keep credentials in SecretStorage and metadata in globalState. Never log SQL or credentials. Never add ANALYZE, telemetry, external services, or webview database access. Batches may contain up to 20 statements. Explain each validated SELECT, VALUES, INSERT, or WITH ending in SELECT or INSERT statement separately, within a read-only transaction and with bounded timeouts. All automated database work must target an isolated test instance. Do not use production credentials.

SQL Server: use dedicated Tedious connections and separate SHOWPLAN_XML ON/query/OFF batches. Never execute submitted SQL with Showplan disabled. Preserve dependent statements inside GO-delimited batches; validate query-only T-SQL and reject SET, dynamic execution and DDL. No read-only transaction is required for Showplan compilation; test all live work against isolated instances only.

AI assistance is explicitly user-authorized: the extension host may call only https://api.openai.com/v1/models and /responses for API-key/model setup and explicit advice requests. Store the API key in SecretStorage, model ID in globalState; never expose keys to webviews, logs, plans or exports. Advice sends the chosen statement and plan only, never connection metadata or unrelated batch SQL. No advice-triggered SQL execution. Validate all webview payloads, bound inputs/responses, and support cancellation. Tests use mock transport unless a dedicated test key is explicitly supplied.

Actual execution is now explicitly authorized by the user for the MVP: a separate confirmed run action may use PostgreSQL EXPLAIN ANALYZE with BUFFERS and COMMIT, or SQL Server STATISTICS XML. Never activate execution from Explain, AI advice, import or export. Bind runtime actions to host-registered live estimated plans and their original connection. Support single SELECT/INSERT only, discard result rows, impose bounded timeouts, never auto-retry, and warn on uncertain write outcomes. Automated execution tests must remain isolated.

Oracle is explicitly authorized as a third connector. Use node-oracledb Thin mode and dedicated connections. Estimated collection uses EXPLAIN PLAN plus PLAN_TABLE reads and rolls back diagnostic writes; it cannot use a read-only transaction. Actual execution collects instrumented cursor statistics for an exact uniquely tagged SQL_ID/child cursor, drains SELECT results, and explicitly commits successful INSERT only after validating the runtime plan. Preserve deadlines, bounded cancellation, original-query binding and uncertain-outcome messages. Do not replay PL/SQL, DDL or script setup. Oracle automated integration is opt-in and fixed to a disposable localhost instance. No AWR/ASH, SQL Monitor or licensed advisor dependency.

Disposable database framework: `npm run test:databases` runs PostgreSQL, SQL Server and Oracle Docker containers sequentially. `npm run test:postgres:docker`, `npm run test:sqlserver:docker` and `npm run test:oracle:docker` run an engine alone; `npm run verify -- --databases` includes them in full verification. Shared Docker lifecycle lives in test/helpers/dockerDatabase.mjs. Keep images pinned, ports localhost-only, credentials generated/unlogged, resources owned by unique labels, and cleanup in finally. Never reuse existing containers/data volumes or prune unrelated Docker resources.

Managed test deployment: `npm run test:databases:up` creates fresh owned PostgreSQL, SQL Server and Oracle containers and leaves them running. `npm run test:databases:run` tests that same explicitly deployed set after ownership, image and localhost-binding validation. `npm run test:databases:down` removes only identities recorded in ignored work/test-databases.json. Preserve that state for interrupted-start recovery; never print its passwords, reuse unrelated containers/volumes, or prune Docker. Lifecycle code remains shared with disposable runners.

Shared sample data: `npm run test:databases:seed` populates only the explicitly managed owned deployment with a deterministic ten-table metadata catalog in dbtuna_sample. Validate every target before writes, retain any existing namespace unless it exactly matches, and never log SQL/data/credentials. PostgreSQL/SQL Server use transactional setup; Oracle uses a schema-only owner and removes only a namespace freshly created by a failed attempt. Verify rows and relationship metadata across all engines.
