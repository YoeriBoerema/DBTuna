# Table relationships

Schemas use an Okabe–Ito-based color-vision-accessible palette with distinct solid/dashed/dotted line patterns, so identity does not depend on color alone. Relationship lines and arrows use the referencing (source) table's schema color, including cross-schema foreign keys. Schema headers show a matching line-pattern sample and name, and table borders match their own schema. Selecting a relationship preserves its color and pattern, thickens its lines and dims the others. Palette colors adapt for light backgrounds. Beyond seven schemas, colors repeat with additional patterns.

This follows the redundant-encoding guidance in [Okabe and Ito's Color Universal Design](https://jfly.uni-koeln.de/color/). Browser checks include deuteranopia simulation, matching legend patterns, and 3:1 line contrast against the reference dark (`#181c25`) and light (`#ffffff`) backgrounds. Custom VS Code themes can have different contrast.

The Database Explorer opens automatically at startup. To disable that behavior, turn off **DBTuna: Always Show Database Explorer** in VS Code Settings (`dbtuna.alwaysShowDatabaseExplorer`). You can reopen it at any time with **DBTuna: Show Database Explorer**.

In **DBTuna Database Explorer**, hover over a database connection and click its **Visualize Table Relationships** action. The diagram opens in its own editor tab using that connection and all its visible schemas. There are no connection or schema prompts.

Each card represents a table and includes its schema name. Columns have separate rows with dividers. Each arrow starts at the foreign-key column and ends at its referenced column. Composite foreign keys draw one line per column pair, sharing the constraint name. Click an arrow to see its name and column mapping. Self-references and cross-schema references are supported; tables referenced but absent from the visible table listing use a dashed border. Cards show the columns participating in relationships, rather than every column in the table.

Drag cards to rearrange the diagram, scroll to zoom, or use the fit-view and minimap controls. Tables without declared foreign keys are included. Only metadata visible to the selected database account is available. Relationships are read from catalog constraints, not inferred from matching column names or table data. Reopen the diagram to reload metadata after database changes.

The automatic layout groups tables in labeled schema regions. It measures rendered card sizes (including wrapped names) and uses ELK's hierarchical layered layout with fixed column ports, crossing minimization and orthogonal routes around tables. Constraint labels appear when a relationship is selected to reduce clutter. Drag a schema region to move its tables together, or drag individual tables inside their region. Use **Auto layout** to restore spacing and recalculate routes after manual moves. Dense or cyclic relationships may still cross; crossing-free layouts cannot be guaranteed.

Connections choose left or right column anchors based on table positions, rather than always leaving right and entering left. Self-references loop on the right. Schema-boundary edge merging is disabled to keep individual relationships distinguishable. Click a relationship to highlight all its column-pair lines and dim other relationships; click empty canvas or press Escape to restore all lines.

After table placement, an independent orthogonal router searches around table obstacles using A*. It scores path length, bends, crossings and shared segments, adds parallel lane candidates, and performs a second improvement pass. It keeps an existing valid route when a better one is not found. The search has per-route and overall work limits so large diagrams can retain some original ELK routes. This is an independent implementation of published routing techniques; it does not include yFiles or libavoid.

Use **Reroute lines** after dragging tables to improve connections without changing table positions. If the current positions leave no safe route within the search limits, the diagram retains the current lines and suggests moving tables apart or using **Auto layout**. The header reports proper line crossings. Shared segments are measured separately in development benchmarks; endpoint touches are not counted as proper crossings.

The viewer supports PostgreSQL, SQL Server and Oracle. Workspace trust is required. Catalog reads run through the existing connector timeout and cancellation paths; credentials stay in the extension host. A diagram supports up to 2,000 tables including referenced tables, and 10,000 foreign-key column mappings across the database (up to 2,000 mappings per schema). Exceeding a limit reports an error instead of silently showing a partial database. The progress notification supports cancellation.
